# Stadtarchiv: Erfassungstool, Plan

Stand: 2026-11-06. Entwurf.

## Ziel

Zehntausende Objects (Fotos, Schriftstücke, später mehr) erfassen. Metadaten
als YAML in einem GitHub-Repo, Dateien in einem S3-kompatiblen Object Store.
Erfassung per Chat mit einem Agenten, Dateien per Drag and Drop.

## Begriffe

- **Object**: ein Stück im Archiv (Brief, Foto). Beschrieben durch eine YAML-Datei.
- **File**: eine Rohdatei im Object Store (Scan, Video, OCR-Text).
- **Variant**: aus einem File abgeleitete Datei (Vorschau, Webgröße, OCR, Keyframe).
- **Claim**: Vermerk im Store, wer ein File gerade bearbeitet.

## Architektur

- **Browser-App**: statische Seite, Svelte mit Vite, TypeScript, CodeMirror 6. Hash, EXIF, Vorschau, Schemaprüfung und YAML-Editor laufen im Browser.
- **Worker** (Cloudflare, TypeScript): prüft das GitHub-Konto, signiert Uploads, verwaltet Claims, leitet Chat-Anfragen an das Modell. Hält alle Geheimnisse. Sieht keine Inhalte.
- **Daten-Repo** (GitHub, öffentlich): YAML pro Object, Entwurfs-PRs, Squash-Merge, CI nur für fertige PRs.
- **Object Store** (S3-kompatibel, öffentlich lesbar): Originale und Varianten unter dem Content-Hash.
- **Modell**: Claude Haiku 5.5 über die Anthropic-API, nur über den Worker.

Die Logik (Hash, Pfade, Schema, YAML-Änderungen, Claim-Client) steht in einem Kernmodul ohne Framework. Browser, Worker und CI benutzen dasselbe Modul.

## Datenmodell

Schema: `object.schema.json` (JSON Schema 2020-12). Typen: `photo`, `document`. Subtype optional, z.B. `letter`, `book`.

- ID: ULID, wird bei Anlage des Entwurfs erzeugt
- Datei der YAML: `objects/<id[-2,2]>/<id>.yml` (nach den letzten Zeichen verteilt, da der Anfang einer ULID der Zeitstempel ist).
- Datum: String, EDTF (`1963-07`, `1960/1969`, `196X`).
- Ort: `location` (Text) und `geocode` (`lat`, `lon`, `precision`).
- File: `role`, `seq`, `path`, `sha256`, `mime`, `bytes`, Maße, `variants`.
- Pfade: `originals/<sha[0,2]>/<sha[2,2]>/<sha>.<ext>`, `variants/...` analog.
- Status ignorieren wir vorläufig (wird z.T. durch den PR Workflow abgebildet).

## Ablauf einer Sitzung

1. Anmelden mit GitHub-Token (pro Person, nur für das Daten-Repo).
2. Entwurf anlegen: ULID, Typ, lokaler Datensatz (IndexedDB), Entwurfs-PR.
3. Datei(en) ablegen: Hash, EXIF, Vorschau im Browser. Prüfung gegen Index und Claim.
4. Upload im Hintergrund, danach Vorschau.
5. Beschreiben der Datei(en) im Chat. Agent liefert Änderungen (Feld, neuer Wert, alter Wert). Die App wendet sie an (und überspringt ggf von Hand geänderte Felder mit einer Meldung).
6. Zwischenstände als Commits auf den Entwurfs-Branch.
7. Einreichen: PR wird fertig, CI läuft, Freigabe nach Teamkonvention.

## Konflikte

- Datei schon in einem gemergten Object (Index): Hinweis mit Link zum Object.
- Fremder Claim: Hinweis mit Name und Zeit. Rückmeldung via UI.
- Claim ist atomar (bedingtes Schreiben). Wenn der Store das nicht kann, HEAD vor dem Schreiben und die CI als Sicherung.

## Prüfungen

Im Browser vor dem Einreichen, in der CI mit demselben Code: Schema, Pfad passt zum Hash, `seq` eindeutig, Dateien im Store vorhanden, keine doppelten Hashes über Objects.

## Worker-Routen

- `GET /session`: Token prüfen, Name und Schreibrecht.
- `POST /claims`: Claim anlegen, signierte Upload-URL mit Uploader-Metadaten.
- `DELETE /claims/<sha256>`: Claim freigeben.
- `POST /variants`: signierte Upload-URLs für Varianten.
- `POST /chat`: Weiterleitung an das Modell, Limit pro Person.

Kein Schreibzugriff auf GitHub. Commits macht der Browser mit dem Token der Person.

## Repos

- `archive-app`: `core/` (Kernmodul, Schema, Tests), `app/` (Svelte), `worker/`.
- `archive-data`: `objects/`, CI-Workflow. Die CI nutzt `core/` in fester Version.

## Tests

Vitest. Zuerst Einheitentests für den Kern, darin Schematests mit gültigen und
ungültigen Beispielen. Dazu einige Worker-Tests für Claims und ein
End-to-End-Test mit Playwright. Weitere Arten bei Bedarf.

## Bauschritte

1. Kern mit Tests.
2. Oberfläche ohne Netz (drei Spalten, Ablage, Editor).
3. Store und Worker (Claims, Upload, Varianten).
4. GitHub (Entwurfs-PR, Zwischenstände, Einreichen, Index).
5. Agent im Chat.

## Entwicklung

Anthropic-Schlüssel `archive-dev`, befristet, Guthaben ohne Auto-Reload als
Obergrenze. Später Wechsel auf ein Konto des Vereins: nur das Worker-Secret
tauschen.
